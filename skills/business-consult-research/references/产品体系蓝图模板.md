# 产品体系蓝图模板

> 用于 AI 机会地图 Skill 的 **Stage 5（产品体系设计）**。
> 从 AI 机会清单中选 Top 1-3 个，输出 MVP + 大产品体系演进蓝图。
> 把研究证据转成可验证的产品系统假设。

---

## 设计原则

遵循以下产品化原则：

1. **从小产品起步，逐步构建成大产品体系**（不一上来就憋大招）
2. **综合考虑 4 个层面**：场景 / 知识库 / 上下文 / Skill
3. **MVP 必须在 6 周内形成可验证闭环**
4. **每个机会必须有回退方案**（失败时沉淀什么可复用）

---

## 4 层规划（每个机会都做一遍）

### 1. 场景层

回答 5 个问题：

1. **谁在什么场景下用？**（具体到时间、地点、设备、心理状态）
   - 例：独立编剧周五晚上在家电脑前，赶下周一交稿的剧本
   
2. **触发使用的事件是什么？**
   - 例：被甲方退稿、自己卡壳、参考要找

3. **完整体验路径**（从打开到反馈）：
   - 打开 → 输入什么 → 看到什么 → 输出什么 → 反馈什么
   
4. **替代了原本的什么动作？**
   - 例：替代了 Google 搜索 + 翻看类似剧本 + 自己拼凑

5. **这个场景一周发生几次？月几次？年几次？**
   - 高频 = 高粘性 = 高 LTV

---

### 2. 知识库层

回答 5 个问题：

1. **产品需要什么领域知识？**
   - 例：剧本结构理论、爆款案例库、行业潜规则
   
2. **知识从哪里来？**
   - 公开数据（爬虫 / 联网）
   - 自建数据（人工整理 / AI 提炼）
   - 用户输入（UGC 沉淀）
   - 合作 / 采购

3. **知识如何更新与维护？**
   - 更新频率：每天 / 每周 / 每月 / 静态
   - 谁更新：自动 / 人工 / 半自动

4. **知识对结果质量的杠杆有多大？**
   - 高：知识库决定 70%+ 质量（如法律咨询）
   - 中：知识库决定 30-50% 质量
   - 低：知识库可有可无，主要靠模型能力

5. **知识库的护城河价值**
   - 时间累积 / 独家来源 / 整理逻辑 / 用户贡献

---

### 3. 上下文层

回答 5 个问题：

1. **单次对话需要哪些上下文？**
   - 用户身份、历史偏好、当前任务、相关案例

2. **跨对话需要记住什么？**
   - 用户的长期偏好、未完成的工作、累积的输入

3. **上下文如何获取、维持、清理？**
   - 获取：用户主动输入 / 自动从历史推断
   - 维持：会话内 cache / 跨会话存档
   - 清理：自动过期 / 用户主动清

4. **上下文长度对成本的影响**
   - 估算单次调用的 token 数 × 单价 = 单次成本
   - 如果是 SaaS，单次成本必须 < 定价的 20%

5. **上下文丢失的后果**
   - 严重：完全失败（如法律案件、医疗诊断）
   - 中等：体验下降但可用
   - 轻微：用户重新输入即可

---

### 4. Skill 层

回答 5 个问题：

1. **产品的核心能力封装为几个 Skill？**
   - 列出 Skill 清单（建议 2-5 个）
   - 每个 Skill 是独立可调用的能力

2. **每个 Skill 的输入输出契约？**
   - 输入格式 + 必填字段
   - 输出格式 + 错误处理

3. **Skill 之间如何调用？**
   - 串行（A → B → C）
   - 并行（A + B 同时跑）
   - 树形（A 触发 B 或 C，二选一）

4. **哪些 Skill 是付费的、哪些是免费的？**
   - 免费引流 Skill：低成本、高频、轻决策
   - 付费核心 Skill：高价值、高频或高决策

5. **Skill 是否可被外部调用 / 集成？**
   - API 暴露范围
   - 集成 MCP / Webhook / Open API

---

## 6 周 MVP 路径

按"先 1 个 Skill → 再 1 个工作流 → 再 1 个完整产品"的节奏：

| 周 | 目标 | 产出物 | 关键动作 |
|----|------|--------|----------|
| Week 1-2 | 核心 Skill 原型 | 最小可用的 1 个 Skill | 跑通核心 prompt + 工具调用 |
| Week 3-4 | 1-2 个种子用户试用 | 真实使用反馈 + 改进点清单 | 主动找用户、记录反馈、快速迭代 |
| Week 5 | 第二个 Skill 加入 | 完整工作流（2-3 个 Skill 串联） | 完成 Skill 间编排 |
| Week 6 | MVP 闭环 | 第一个收费 / 验证客户 | 拿到至少 1 个付费意向或免费长期使用 |

**强制要求**：
- Week 2 末必须有 demo 视频或 GIF 截图
- Week 4 末必须有用户反馈清单（含原话）
- Week 6 末必须有"第一个客户" 或 "明确放弃" 的二元结论

---

## 大产品体系演进路径

从 MVP 起，描述 4 个时点的产品形态：

| 时点 | 产品形态 | 用户规模 | 商业模式 | 关键风险 |
|------|----------|----------|----------|----------|
| Month 1.5（MVP） | 单 Skill | 1-2 个测试用户 | 免费试用 | 没人用 |
| Month 6 | 多 Skill 组合 | 5-20 个付费 | 订阅 / 项目制 | 留存差 |
| Year 1 | 完整产品 + 自助平台 | 50-200 | SaaS | 增长慢 |
| Year 2 | 行业级产品 | 500+ | SaaS + 企业版 | 被巨头跟进 |

每个时点描述：
- **产品里有什么**（功能列表）
- **谁在用**（用户画像变化）
- **怎么收钱**（定价模型 + 客单价）
- **风险在哪**（最大风险 + 对策）

---

## 风险与回退

每个产品蓝图必须含：

### 3 个风险

| 类型 | 描述 | 应对方案 |
|------|------|----------|
| 技术风险 | 例：模型能力不够 / 成本失控 | 例：降级 / 换模型 / 改变形态 |
| 客户风险 | 例：付费意愿低 / 留存差 | 例：转换模型 / 找新场景 / 暂停 |
| 竞争风险 | 例：被巨头跟进 / 同质化 | 例：垂直深耕 / 服务化 / 退出 |

### 回退方案

**如果 MVP 失败，沉淀下来什么可复用？**
- 知识库（行业 know-how）
- 用户关系（即使没买，也建立了认知）
- 技术组件（Skill / 工具 / 流程）
- 认知资产（这个机会为什么不成立）

**强制要求**：每个机会必须有"失败也不亏"的回退资产清单。

---

## 输出格式

整理成 Markdown 文档，存到：
`research/08-s5-product-architecture.json`

按机会逐个展开，每个机会包含：
- 机会基本信息（名字 / 痛点 / 角色 / 综合分）
- 4 层规划全文
- 6 周 MVP 路径表
- 大产品体系演进路径表
- 风险与回退

---

## 调用方注意事项

- 4 层规划的 20 个问题（5+5+5+5）必须**全部回答**，不能跳过
- 6 周 MVP 路径必须可执行（每周有明确产出物）
- 演进路径不要画大饼，每个时点要可证伪
- 风险必须基于行业现状、用户证据与交付能力，不要泛化
- 回退资产必须具体（不是"学到经验"，而是"得到 X 知识库 + Y 用户关系"）
